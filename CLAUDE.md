# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a reusable **template repository** for Roblox game projects (Rojo + Wally), not a specific
game. The `Profile` vertical slice (player data via ProfileStore/Replica, synced into a Charm atom) is
the reference implementation of the architecture below — copy its pattern for new features, and keep
its data shape (`Currencies.Cash`) minimal/generic rather than adding game-specific fields here; those
belong in the concrete game project created from this template.

## Commands

Tools are pinned in `rokit.toml` (rojo, StyLua, wally, selene, blink) and installed via [Rokit](https://github.com/rojo-rbx/rokit):

```bash
rokit install          # install pinned toolchain
wally install          # install packages into Packages/ and ServerPackages/ (both gitignored)
rojo build -o "roblox-game-template.rbxlx"   # build a place file from src/
rojo serve              # serve the project for Roblox Studio to sync live
rojo sourcemap default.project.json -o sourcemap.json   # regenerate sourcemap.json (used by selene/tooling)
selene src              # lint (std = "roblox", configured in selene.toml)
stylua src              # format (tabs, double quotes, 120 col width — see stylua.toml)
```

There is no test runner configured in this repo yet.

`Packages/` and `ServerPackages/` are gitignored — they're regenerated by `wally install` from `wally.toml`/`wally.lock`, not hand-edited.

## Architecture

This template follows architectural conventions validated on a previous project. The codebase is
mid-migration towards the fully intended structure — see "Current implementation status" below for
what's already in place vs. what new code should follow.

### Intended folder structure

Features are split across the three `src/` contexts. Shared cross-cutting concerns (store, network
types, core types) live in `src/Shared/`. Server and Client each get a **`Core/`** folder for
domain infrastructure that isn't itself a gameplay feature — e.g. the Profile system, which almost
every feature ends up depending on for player data. On the server this is also the one exception to
"features don't require each other" (see Key Rules → Features): server features `require` Core
services directly. On the client, features don't `require` Core controllers directly — they read
Core-owned state through the Store, same as with any other Controller — so a module lives in
`Client/Core/` because it's foundational plumbing (e.g. bridges Replica → Store) rather than because
something else requires it directly.

```
src/
├── Shared/
│   ├── Store/               # Charm state (client-readable)
│   │   ├── init.luau        # Root store combining all atoms
│   │   └── Atoms/           # One atom per domain
│   ├── Network/
│   │   └── Types.luau       # Blink payload types (shared)
│   ├── Types/                # Domain types (Profile, Config, Action…)
│   ├── Config/                # Balancing, IDs, prices — never hardcoded in Services
│   ├── Enums/
│   └── Utils/                # Pure utility modules
│
├── Server/
│   ├── Bootstrap.luau        # Server entry point, Loader discovers all Services
│   ├── Network/
│   │   └── init.luau         # Blink.server({…}) — single point of event declaration
│   ├── Signals/               # Cross-feature decoupled events (ProfileSignals, …)
│   ├── Core/                  # Infra that ANY feature can require directly
│   │   ├── ProfileService/    # DataStore, Replica, Action handlers
│   │   └── AnalyticsService/
│   └── Features/
│       └── <feature>/
│           ├── <Feature>Service.luau
│           ├── Actions/        # Isolated handlers for profile mutations (one action each)
│           └── Components/     # *Component modules (Component lib) for CollectionService-tagged Instances
│
└── Client/
    ├── Bootstrap.luau         # Client entry point, loads all controllers
    ├── Network/
    │   └── init.luau          # Blink.client() — mirrors server namespace
    ├── Core/                   # Domain plumbing (Replica → Store bridges, etc.), not gameplay features
    │   └── ProfileController/
    ├── Utils/                  # Standalone client scripts, e.g. UIScaler.client.luau
    └── Features/
        └── <feature>/
            ├── <Feature>Controller.luau
            └── Components/     # *Component modules (Component lib) for CollectionService-tagged Instances
```

### Dependency stack

Core architectural stack (all already in `wally.toml`, except Blink which is a Rokit compiler tool):

| Library | Role |
|---|---|
| **Blink** | Typed binary networking — much faster than raw RemoteEvents |
| **Charm** | Reactive state management (atoms) — single source of truth for shared client state |
| **Replica** | Automatic server→client sync of profile data (via DataStore) |
| **ProfileStore** | DataStore wrapper with exclusive per-player sessions |
| **Component** | Managed lifecycle for **world/map objects** (CollectionService tags) — not for UI |
| **Janitor** | Resource cleanup; always called in `Stop()` / `Destroy()` |
| **Loader** | Auto-require of Services and Controllers via `OnStart()` |
| **Promise** | Async handling |
| **Cmdr** | Debug/admin console |

> UI is built directly in Roblox Studio (ScreenGuis/Frames authored by hand in the Explorer), not
> generated from code. `Component` is unrelated to UI — it only manages behavior of world Instances
> (lava, platforms, triggers) via CollectionService tags. `src/Client/Utils/UIScaler.client.luau` is a
> standalone script (runs itself, not Loader-driven) that auto-scales Studio-built UI: tag a `UIScale`
> with `ScaleComponent` and set its `BaseResolution` (and optional `MinScale`) attributes to have it
> track the viewport; tag a `UIGridStyleLayout`/`UIListLayout` with `ScrollingFrameLayoutComponent` and
> point an `ScaleComponentReferral` ObjectValue at the relevant `UIScale` to keep a ScrollingFrame's
> `CanvasSize` correct under scaling.

Additional gameplay libraries already in `wally.toml` (not part of the core architecture pattern,
evaluate case by case whether a given feature needs them): `ZonePlus` (zone/region detection),
`EzVisualz` (visual effects), `CameraShaker` (camera shake), `RagdollSystem`, `ShapecastHitbox` (hit
detection), `TopbarPlus` (topbar UI icons).

### Data flow

```
Client (Studio-built UI) <--Controller reads-- Charm Atom <--Controller-- Replica <-- Server (ProfileStore)

Client ──► Network.XRequest.Fire(payload) ──► Server validates ──► mutates ProfileStore
Server ──► Network.XSync.FireAll(data)   ──► Controller writes atom ──► Controller updates UI instance properties
```

Fundamental rules:
- The server is always the source of truth.
- The client never mutates state directly — it invokes via Blink and waits for sync.
- An atom is only written by the Controller responsible for that data bridge (Replica/Blink);
  everything else only reads.

### Current implementation status

The Profile vertical slice already exists and is the reference example for the patterns above:

- `src/Server/Bootstrap.server.luau` is the server entry point. It uses the `Loader` package to
  auto-discover `*Service` modules under both `Server/Core/` and `Server/Features/` (started via
  `OnStart`), and `*Component` modules under `Server/Features/`.
- `src/Server/Core/ProfileService/` (`ProfileTemplate.luau`, `ProfileService.luau`) holds the Profile
  infrastructure — it's here rather than under `Features/` because most other server features will
  need to `require` it directly to read/mutate player data.
- `ProfileService` starts a `ProfileStore` session per player on join and wraps `session.Data` in a
  `Replica` for replication; player state (`{ Janitor, Session, Replica }`) is cleaned up via
  `Janitor` on `PlayerRemoving`/session end.
- `src/Server/Signals/` centralizes cross-feature server events (`Signal` package). `ProfileService`
  fires `Signals.ProfileSignals.Loaded` once a profile is ready — subscribe here instead of polling
  player data. New signal modules go in `Server/Signals/` and get re-exported from
  `Server/Signals/init.luau`.
- On the client, `src/Client/Features/Loading/init.client.luau` is the Loader-driven bootstrap — it
  waits for `game:IsLoaded()`, removes the default loading screen, then discovers `*Controller`
  modules under both `Client/Core/` and `Client/Features/` (started via `OnStart`) and `*Component`
  modules under `Client/`. It lives under `Features/` (not at the `Client/` root) because it's
  expected to grow its own loading-screen UI later, making it a real feature rather than pure
  bootstrap plumbing. `src/Client/Bootstrap.client.luau` is a second, simpler entry script that only
  sets one-off GUI settings (disabling the core Backpack, forcing landscape orientation) — it doesn't
  use `Loader`.
- `src/Client/Core/ProfileController/ProfileController.luau` calls `Replica.RequestData()` /
  `Replica.OnNew("Profile", ...)` and mirrors data into the Charm atom at
  `src/Shared/Store/Atoms/ProfileAtom.luau` on load and on every `replica:OnChange`. UI/state should
  read from `Store.Profile`, never talk to `Replica` directly. It lives under `Client/Core/` rather
  than `Client/Features/` because it's domain plumbing other systems rely on indirectly (through the
  Store), not a standalone gameplay feature.
- There is no `Network/` (Blink) layer yet — this is the piece to add as the project grows into the
  target structure described above.
- `src/Client/Utils/UIScaler.client.luau` is a standalone script (runs itself on require, not
  Loader-driven) that auto-scales UI built directly in Roblox Studio — see the Dependency stack note
  above for the tagging/attribute convention it relies on.
- `src/Shared/Types/` holds one module per logical type (e.g. `ProfileType.luau`), re-exported through
  `src/Shared/Types/init.luau`. Keep adding new shared types this way rather than inlining type
  definitions in feature code.

## Key Rules

### State (Charm)

- Never mutate an atom's table in place — always build a new table (`table.clone` + changes) and call
  the atom with it. Charm's change detection is by **reference**; mutating in place and re-writing the
  same reference makes Charm think nothing changed, so nobody gets notified.
- Use `Charm.computed(fn)` for derived state consumed in **more than one place** (it's memoized and
  shared). For a selector used only once, an inline function in `subscribe`/`effect` is enough.
- Prefer `Charm.effect(fn)` over `subscribe` when you need the logic to run immediately **and** on
  every change — avoids duplicating the initial manual call plus the `subscribe` listener.
- Use `Charm.peek(atom)` for one-off reads inside event handlers (clicks, etc.) — makes it explicit
  that the read shouldn't become a reactive dependency.
- Always subscribe/derive from the narrowest slice of state you need, not the whole root atom.
- Always dispose the cleanup function returned by `subscribe`/`effect` (via Janitor) when the
  component/controller is destroyed.

### UI (Studio-built)

- UI is authored directly in Roblox Studio's Explorer (ScreenGuis, Frames, etc.), not generated
  declaratively in code.
- Controllers reference the Studio-built instances (e.g. `PlayerGui:WaitForChild(...)`) and bind Store
  state to instance properties manually via `Charm.subscribe`/`Charm.effect` — there is no
  Vide/`useAtom`-style bridge, so the subscription's cleanup function must be disposed via Janitor
  explicitly.
- Tag scalable UI with `ScaleComponent`/`ScrollingFrameLayoutComponent` following the conventions in
  `src/Client/Utils/UIScaler.client.luau` so it participates in automatic viewport scaling.

### Networking

- Validate all data received on the server — the client is never trusted.
- The server is always the source of truth; the client only reacts.
- Define every event/function in `Server/Network/init.luau`; never create RemoteEvents manually.

### Features

- Features don't `require` each other — they communicate via the Store or Signals.
- Server exception: anything under `Server/Core/` (e.g. ProfileService, AnalyticsService) can be
  `require`d directly by any server feature — it's infrastructure, not a lateral peer. The "don't
  require each other" rule is about **lateral** coupling between features (e.g. a TrollItem feature
  depending on a Match feature), not about depending on base services.
- Client `Core/` is different: nothing requires a Core controller directly (that would recreate lateral
  coupling on the client). It holds foundational plumbing like `ProfileController`, which just keeps
  the Store in sync — other client features consume that data by reading the Store, never by
  requiring the Core controller itself.
- Action handlers are pure-ish functions: take a payload, run logic, return a result. No globals.
- Controllers are thin: wire UI events to Blink calls and subscribe the Store to components.

### Profile Actions

- Action handlers never yield (no `task.wait`, no async calls) — they run synchronously inside
  `pcall`. Yielding would break the single-threaded update guarantee.
- Use template strings (backticks) for all string interpolation — never `..`.

### General conventions

| Pattern | Where |
|---|---|
| `local Private = {} / local Shared = {}` | All services and controllers |
| `_fieldName` | Private fields in OOP types/components |
| `SCREAMING_SNAKE_CASE` | Constants at the top of files |
| Template strings (backticks) | All string interpolation |
| Janitor in every lifecycle | Cleanup of events, subscriptions, instances |
| `task.spawn` for blocking calls | Avoid blocking `OnStart()` |
| `os.time()` server-side | Persisted timestamps |
| `os.clock()` client-side | Local countdown anchors |
